OtonumaASIO マニュアル

音沼の住民に向けた、DAC への受け渡しを細かく追い込むための仮想 ASIO ドライバ。再生ソフトからは普通の ASIO ドライバ 1 本に見え、その裏で DAC への受け渡し方式とバッファ・周期を、再生しながら切り替えて好みの音を探すための仮想 ASIO ドライバです。版 1.1.1。

概要

1.0.x までは「BareStream Local」という名前でした。1.1.0 から OtonumaASIO に変わり、再生ソフトの出力先の名前も「OtonumaASIO」になります。install.bat は旧名の登録・常駐・ショートカット・フォルダを自動で片付け、設定とプリセットは初回起動時に自動で引き継ぎます。
  • ビットパーフェクト: 音量・ディザ・リサンプルは一切しません。形式変換は整数のコンテナ詰め替え（32bit → 詰めた 24bit など）だけで、削る下位ビットに 0 以外が入っていれば警告します。
  • ユーザーモードだけで完結: カーネルドライバを作らないので、ドライバ署名は不要です。DLL を登録するだけで動きます。
  • 出口を選べる: ASIO 中継・WASAPI 排他・Kernel Streaming（パケット方式 / WaveRT 方式）・試験用の null。
  • 確かめられる: 起床間隔のばらつき、アンダーラン、パイプライン内のビット一致を常時表示し、ブラインド A/B（ABX）で本当に聞き分けられるかを統計的に判定できます。
  • 対象: Windows 10 / 11 x64。32bit の再生ソフト向けに 32bit 版 DLL も同梱しています。

仕組み

再生ソフトへのコールバック（bufferSwitch）は、DAC ではなく自前のポンプスレッドが駆動します。再生ソフトから受け取ったデータはいったんリングバッファに入り、別の出力スレッドが「受け渡し周期」ごとに出口（ドライバ）へ渡します。この 2 段構えのおかげで、再生ソフト側のバッファと DAC 側の受け渡しを独立に調整できます。

USB の転送そのもの（ハイスピード USB では 125 µs ごとのマイクロフレーム）と、1 パケットあたりのサンプル数（非同期 USB DAC では DAC からのフィードバックで決まる）、DAC のクロックは、どのパラメータでも変わりません。変えられるのは「PC の中で、いつ・どれだけの量を・どの経路で」ドライバへ渡すか、です。

インストール

バッチファイルでインストールする（おすすめ）

  1. zip を展開したフォルダの install.bat をダブルクリックします。管理者権限の確認（UAC）が出るので「はい」を選びます。
  2. 次のことを自動で行います: C:\Program Files\OtonumaASIO\ へのコピー、ASIO ドライバの登録（64bit / 32bit）、スタートメニューへのショートカット作成（コントロールパネル・マニュアル・アンインストール）。
  3. 「Windows の起動時にコントロールパネルをタスクトレイに常駐させますか」と聞かれるので、Y（常駐する）か N を押します。
  4. 最後にコントロールパネルが開きます。

アンインストールは、スタートメニューの「OtonumaASIO アンインストール」または uninstall.bat を実行します。ドライバの登録解除、常駐とショートカットの削除、インストール先フォルダの削除を行い、設定（プリセットを含む settings.json）を消すかどうかを確認します。

どちらも、再生ソフトがドライバを使っている間は実行できません（使用中と表示されたら、再生ソフトを終了してからやり直してください）。常駐の設定はバッチを実行したユーザーに対して行います。管理者に昇格するとき別のアカウント名を入力した場合は、常駐はパネルの右クリックメニューから設定し直してください。

手動でインストールする

  1. DLL 2 つ（OtonumaASIO64.dll・OtonumaASIO32.dll）と OtonumaPanel.exe・otonumareg.exe を同じフォルダに置きます（例: C:\Program Files\OtonumaASIO\）。登録後にフォルダを動かすと動かなくなるので、先に置き場所を決めます。
  2. コマンドプロンプトでそのフォルダに移り、otonumareg install を実行します（管理者権限の確認が出ます）。
  3. otonumareg status で 64bit / 32bit の登録先が出れば完了。解除は otonumareg uninstall。

再生ソフト（TuneBrowser / foobar2000 など）の出力先に OtonumaASIO が現れます。

未署名の DLL なので、ウイルス対策ソフトがブロック・誤検知することがあります。その場合は配置フォルダを検査の除外に追加してください（ESET: 詳細設定 → 検出エンジン → 除外 → パフォーマンスの除外）。

更新するときは、再生ソフトを終了してから DLL（64 / 32）と OtonumaPanel.exe を上書きします。置き場所が同じなら otonumareg install のやり直しは不要です。DLL と OtonumaPanel は計測データの形式を共有しているので、必ず両方そろえて入れ替えてください。

ビルド

Visual Studio 2026

  1. 「C++ によるデスクトップ開発」ワークロード（MSVC v145・Windows SDK）を入れます。
  2. OtonumaASIO.sln（または新形式の OtonumaASIO.slnx）を開きます。
  3. 構成 Release、プラットフォーム x64 でビルド。続けて x86 でもビルドします。
  4. 出力: bin\x64\Release\ に 64bit 版一式、bin\Win32\Release\OtonumaASIO32.dll に 32bit 版 DLL。

設定の要点: ツールセット v145、C++17、/utf-8、Unicode、ランタイム静的リンク（/MT、VC++ 再頒布パッケージ不要）。Steinberg ASIO SDK は不要です（IASIO は自前定義）。

CMake

cmake -B build -A x64 && cmake --build build --config Release
cmake -B build32 -A Win32 && cmake --build build32 --config Release

mingw-w64 でのクロスビルドにも対応しています（開発時の検証はこれと Wine で行っています）。

使い方

  1. 再生ソフトの出力先を OtonumaASIO（ASIO）にします。
  2. OtonumaPanel.exe を開きます（再生ソフトの ASIO 設定ボタンからも開けます）。
  3. 出力方式・出力デバイスを選んで「適用」。
  4. 再生しながら受け渡し周期や駆動方式を変えて聴き比べます。右上に「いま何が起きているか」が出ます。

パネルの各項目の右にある記号が反映のしかたです。

記号意味
即すぐ反映。音は途切れません。
開出力（ドライバ側）だけ開き直します。一瞬途切れます。
再再生ソフトに再初期化を要求します。多くの再生ソフトは自動で開き直し、1〜2 秒途切れます。

タスクトレイ常駐

OtonumaPanel.exe は起動するとタスクトレイ（通知領域）にアイコンを置きます。ウインドウの × や最小化ではトレイに格納され、終了はしません。

操作動作
アイコンをクリックコントロールパネルを開く
アイコンにマウスを載せる状態（再生中のレート・形式・出力方式、アンダーランの回数）を表示
右クリック →「プリセットを適用」保存したプリセットをその場で適用（反映のしかたは通知で表示）
右クリック →「Windows の起動時に常駐する」オンにすると、サインイン時にトレイに格納した状態で起動します（HKCU\…\Run に登録。オフで登録を消します）
右クリック →「終了」パネルを終了します（ドライバの動作には影響しません）

アイコン右下の丸で状態が分かります。

表示状態
丸なし再生ソフトで OtonumaASIO が使われていない
灰色使われているが停止中
緑再生中
橙再生中で、直近 10 秒以内にアンダーランが起きた

パネルを開いている間は表示を毎秒 5 回更新しますが、トレイに格納している間は状態の読み取りを 2 秒に 1 回まで落とし、再生中の PC の起床を最小限にします。再生ソフトの ASIO 設定ボタンを押したときも、常駐中のパネルが開きます。コマンドラインで OtonumaPanel.exe /tray とすると、ウインドウを開かずトレイに格納した状態で起動します。

出力方式経路周期を決めるものDSD
ASIO 中継OtonumaASIO がホストになってベンダーの ASIO ドライバを開き、その上で流すベンダー ASIO のバッファサイズ（ドライバが許す値に丸める）ネイティブ / DoP
WASAPI 排他IAudioClient の排他モード。Windows のオーディオエンジン（ミキサー）を通らないデバイス周期（最小周期と整列の制約あり）DoP

なぜ KS や WASAPI ではネイティブ DSD にならないのか: Windows 標準の USB オーディオクラスドライバ（usbaudio2.sys）や WASAPI には DSD のビット列をそのまま渡す形式がありません。そのため PCM の箱に DSD を詰める DoP（DSD over PCM）を使います。DAC 側の表示が DoP になるのは正常です。ネイティブ DSD が使えるのは、ベンダーの ASIO ドライバが対応している場合の ASIO 中継だけです。ただし、ベンダーのドライバが USB に送る段階で DoP に変換している場合もあり、そのときは DAC の表示が DoP になります（OtonumaASIO からは切り替えられません）。

出力方式ごとの注意

  • KS: Windows の共有モード（audiodg）がそのデバイスを使っていると、ピンが開けません。Windows の「サウンド」設定で既定のデバイスを別の出力先にしてください。
  • WASAPI 排他: デバイスのプロパティ → 詳細 →「アプリケーションによりこのデバイスを排他的に制御できるようにする」にチェックが必要です。
  • ASIO 中継: 中継先は HKLM\SOFTWARE\ASIO に登録されたドライバから選びます（自分自身は除外）。USB 側のバッファ（ストリーミングモードなど）は「ベンダーのコントロールパネル」ボタンから変更します。

パラメータ詳解

それぞれのパラメータについて、何を決めるのか、値を上げる・下げると PC の中で何が起きるのかを説明します。「音がどう変わるか」は聴き手と機器によって異なり、確立した測定上の根拠がないものも多いため、音の好みから設定を探すの章で分けて扱います。

出力方式・出力デバイス 再

既定: KS（自動選択） / デバイスは前回値
決めるもの
リングから DAC ドライバへ渡す経路（API）と相手のデバイス。
技術的な違い
経路ごとに、ドライバの中を通る層の数と、データを渡すときの起床のしかたが違います。ASIO 中継はベンダー独自のドライバのスケジューリングに従い、ベンダーのバッファ設定がそのまま効きます。WASAPI 排他はオーディオエンジンを迂回しますが、WASAPI の層と整列の制約が残ります。KS パケットは WASAPI の層も通らず、ドライバのピンへ直接 IRP（I/O 要求）を送ります。KS WaveRT はドライバのバッファに直接書くので、データの受け渡しに I/O 要求すら発生しません（位置の読み取りだけ）。
選び方
まず確実に鳴る WASAPI 排他で基準を作り、KS（D400EX ではパケット方式）と ASIO 中継を比べるのが手堅い進め方です。DSD をネイティブで送りたいなら ASIO 中継です。

ホスト側バッファ 再

範囲: 32〜32768 サンプル（2 のべき乗） / 既定: 1024
決めるもの
再生ソフトに渡す ASIO バッファの長さ。再生ソフトが 1 回のコールバックで作る量で、再生ソフトのデコード・DSP スレッドが起きる回数（= サンプルレート ÷ この値 回/秒）を決めます。
出力側との関係
DAC への受け渡しとは独立です。ここを小さくしても DAC 側の周期は変わりません（それは受け渡し周期の役目）。
大きくすると再生ソフトの起床が減り、1 回の処理がまとめて行われます。CPU の割り込み・切り替えは減り、遅延（再生位置と実際の音のずれ、シークの反応）は増えます。
小さくすると再生ソフトが細かく頻繁に起きます。遅延は減りますが、ポンプスレッドと再生ソフトのスレッド切り替えが増え、CPU 負荷が上がります。極端に小さいと間に合わずアンダーランします。
DSD のとき
DSD では、DSD のレートに比例させて最低約 5.8 ms ぶん（この値 1024 相当）を提示します。DSD256 で 32 サンプル（約 45 µs）のような設定は毎秒 2 万回以上の呼び出しになり破綻するためです。
目安
1024〜4096。遅延を気にしないなら大きめが安定します。

受け渡し周期（Hz） 開

範囲: 1〜1000 / 既定: 10（JPLAY の「10 Hz（基準）」に合わせた値）
決めるもの
出力スレッドがドライバへデータを渡す頻度。1 回に渡す量 = サンプルレート ÷ 指定 Hz です（44.1 kHz なら 10 Hz → 4410 サンプル ≒ 100 ms、700 Hz → 63 サンプル ≒ 1.4 ms）。実際の値は出口が受け付ける最も近い値に丸め、パネルに「指定値 → 実効値」を出します。
出口ごとの意味
ASIO 中継: ベンダー ASIO のバッファサイズ（2 のべき乗などに丸まる）。WASAPI 排他（イベント）: デバイス周期 = バッファ長。デバイスの最小周期（USB DAC では 3 ms 前後が多い）より短くはできません。KS パケット: 1 パケットの長さ。KS WaveRT（通知あり）: 循環バッファの半分。タイマー駆動: タイマーの周期。
高くすると（1 回の量が小さい）出力スレッドの起床・ドライバへの I/O 要求・割り込みが 1 秒あたり増えます。データは小分けに途切れなく流れ、ドライバ内に溜まる量（遅延）が減ります。その代わり 1 回の遅れの許容時間が短くなり、アンダーランしやすくなります。CPU が深い省電力状態（C ステート）に入る時間も減ります。
低くすると（1 回の量が大きい）起床はまれで、そのたびにまとまった量を一気に渡します。CPU は長く休めますが、渡す瞬間はメモリとバスの動きが集中します。遅延は増え、設定変更やシークの反応も遅くなります。アンダーランには強くなります。

ポンプモード・先読み量 即

ポンプモード: 同期 / 先読み（既定: 同期） ・ 先読み量: 0.05〜2 秒（既定 2、先読みモード時に有効）
決めるもの
リングバッファにどれだけ溜めておくか。同期モードはホスト側バッファ 2 つ分程度だけ溜め、出口が消費したぶんだけ再生ソフトを呼びます（普通の ASIO と同じ振る舞い）。先読みモードは指定秒数ぶんを溜めておき、再生ソフトが一時的に遅れても（ディスクやネットワークの待ち、他の処理）出口は影響を受けません。
先読み量を増やすと再生ソフトの一時的な停止に強くなります。ただし溜めた量だけシーク・曲送り・一時停止の反応が遅れて聞こえ、メモリも使います（384 kHz / 32bit / 2ch で 1 秒あたり約 3 MB）。容量を超えて増やしたときは、リングを作り直すため一瞬音が飛びます。
同期モード・少なめにすると操作への反応が速く、遅延が小さくなります。再生ソフト側の遅れがそのままアンダーランにつながりやすくなります。
曲送りの表示がずれる
再生ソフトから見ると、曲の最後のデータを渡し終えた時点で曲が終わったことになるので、まだ前の曲の最後（先読み量の秒数ぶん）が鳴っているうちに次の曲の表示に進みます。OtonumaASIO はドライバなので曲の区切りを知ることができず、これは先読みの仕組み上避けられません。そのため先読み量の上限は 2 秒にしています。曲全体を RAM に載せてから鳴らしたい場合は、再生ソフト側の機能（foobar2000 の Full file buffering など）を使う方が、表示がずれず筋がよい方法です。
補足
溜まりきった後は、先読みモードでも再生ソフトを呼ぶ平均の頻度は同期モードと同じです（消費したぶんを補充するため）。先読みは「余裕」を増やす設定で、処理の総量を減らすものではありません。後から書き込む再生ソフト（パネルに「後から書き込み」と出る）では、溜まる速さが実時間の約 1.3 倍までになります。

駆動方式 開

イベント / タイマー / タイマー＋スピン（既定: イベント）
決めるもの
出力スレッドを何をきっかけに起こすか。
イベント
ドライバからの通知（I/O 完了やバッファ境界の通知）で起きます。起きるタイミングはドライバとハードウェアが決め、PC 側のタイマーには依存しません。ASIO 中継は常にこの方式です（ベンダードライバのコールバックで起きる）。
タイマー
高分解能の待機タイマー（CREATE_WAITABLE_TIMER_HIGH_RESOLUTION）で定周期に起きます。WASAPI では GetCurrentPadding で空きを見ながら書き足し、ドライバ内のバッファを周期の数倍持てるので、短い周期でもイベント駆動より余裕があります。WASAPI でドライバが受け付けないときは、受け付けられる組み合わせを順に試し、パネル 3 行目に使ったものを表示します。
タイマー＋スピン
タイマーで少し手前まで眠り、最後の数十 µs はビジーウェイトで待ちます。起床時刻のばらつきは最小になりますが、待っている間 CPU コアを 1 つ使い続けます（消費電力・発熱・ファンの回転が増えます）。
起床時刻のばらつき（パネルのヒストグラム）は PC 内のスケジューリングのばらつきで、DAC の出力ジッターとは別物です。非同期 USB の DAC では、実際の再生タイミングは DAC 自身のクロックが決め、PC の起床のばらつきはドライバと DAC 内のバッファで吸収されます。

KS キュー深さ 開

範囲: 2〜16 / 既定: 4（KS パケット方式で有効）
決めるもの
ドライバへ送り込んでおくパケットの数。1 つが完了するたびに次のデータを詰めて送り直すので、常にこの数だけドライバの中に待機しています。
増やすと出力スレッドが一時的に遅れてもドライバ側のデータが尽きにくくなります。遅延は「1 パケットの長さ × 数」だけ増えます。受け渡し周期を高くする（パケットを小さくする）ときは増やすのが定石です。
減らすと遅延は減りますが、余裕が「パケット 1〜2 個分」しかなくなり、高い周期ではアンダーランしやすくなります。

WaveRT 書き込み先行量（ms） 即

範囲: 1〜500 / 既定: 20（KS WaveRT のタイマー駆動・通知なしのとき有効）
決めるもの
ハードウェアの再生位置より何 ms 先までデータを書いておくか。再生位置は位置レジスタの直読み（なければ位置プロパティ）で取ります。
増やすと余裕が増え、追い越し（アンダーラン）に強くなります。遅延も増えます。
減らすと遅延は減りますが、出力スレッドの起床が遅れたときに再生位置に追い越されやすくなります。追い越されたらアンダーランとして数えます。

出力スレッド優先度 即

MMCSS Pro Audio / MMCSS Pro Audio＋Critical / TimeCritical（MMCSS なし）（既定: ＋Critical）
決めるもの
出力スレッドが CPU を取り合う強さ。
MMCSS Pro Audio
Windows のマルチメディアクラススケジューラに「プロオーディオ」として登録し、一定時間はリアルタイム帯の高い優先度に引き上げてもらいます。
＋Critical
MMCSS の中でもさらに上の優先度（AVRT_PRIORITY_CRITICAL）。他の MMCSS スレッド（他の再生ソフトなど）より先に動きます。
TimeCritical
MMCSS を使わず、通常のスレッド優先度の最上位（THREAD_PRIORITY_TIME_CRITICAL）にします。MMCSS の時間制限は受けませんが、リアルタイム帯の MMCSS スレッドよりは下になります。
補足
優先度を上げても処理が速くなるわけではなく、「呼ばれたらすぐ動ける」ようになるだけです。ASIO 中継では出力スレッドはベンダードライバのものなので、この設定は効きません。

CPU コア固定 即

自動 / コア番号（既定: 自動）
決めるもの
出力スレッドを特定の論理プロセッサーだけで動かすか。
固定するとコア間の移動がなくなり、キャッシュの再読み込みが減って起床後の処理時間が安定します。USB の割り込み処理（DPC）が集中するコアとは別のコアを選ぶと効果的です。Core i7-14700F のような P コア / E コア混在の CPU では、一般に番号の若い側が P コアです（タスクマネージャーやデバイスの情報で確認してください）。
自動にするとWindows が空いているコアを選びます。たまたま忙しいコアや E コアに載ると、起床から処理までの時間がばらつくことがあります。

タイマー分解能 即

OS 既定 / 1 ms / 0.5 ms（既定: OS 既定）
決めるもの
Windows のタイマー割り込みの間隔（timeBeginPeriod / NtSetTimerResolution）。システム全体に効きます。
細かくすると通常のスリープやタイマーの精度が上がります（高分解能タイマーを使う本ドライバのタイマー駆動にはもともと影響は小さめ）。タイマー割り込みが 1 秒あたり 1000〜2000 回に増え、CPU が深く休めなくなり、消費電力が増えます。
OS 既定にするとWindows に任せます（最近の Windows は必要なプロセスにだけ細かい分解能を割り当てます）。

メモリ固定（VirtualLock） 開

オン / オフ（既定: オン）
決めるもの
リングバッファと KS パケット用のメモリを物理メモリに固定するか。
効果
オンにすると、メモリが足りなくなったときにリングがページファイルへ追い出され、読み出し時にページフォールト（ディスク待ち）が起きることを防ぎます。オフでも普段は問題ありませんが、メモリが逼迫したときの保険になります。固定に失敗しても動作は続け、パネルにメッセージを出します。

DSD の送り方・DoP 上限 再

送り方: 自動 / ネイティブ / DoP（既定: 自動） ・ DoP 上限: DSD64 / DSD128 / DSD256 / DSD512（既定: DSD256）
決めるもの
再生ソフトから受け取った ASIO ネイティブ DSD を、出口へどう渡すか。
自動
ASIO 中継で相手のドライバがネイティブ DSD に対応していればネイティブ、そうでなければ DoP。
DoP
DSD 16 ビットぶんを 24bit PCM の下位 16 ビットに入れ、上位 8 ビットに目印（0x05 / 0xFA を交互）を入れます。PCM レート = DSD レート ÷ 16（DSD64 → 176.4 kHz、DSD256 → 705.6 kHz）。DAC が対応する PCM レートの上限で、DoP で送れる DSD の上限が決まります。
DoP 上限
DoP で送ってよい DSD レートの上限です。これを超える DSD は、DoP で送ることになる出口（KS・WASAPI・ネイティブ非対応の ASIO 中継）では再生ソフトに「非対応」と返します。再生ソフトが DSD256 や PCM への変換に切り替えられるようにするためです。DSD512 の DoP は 1411.2 kHz の PCM が必要で、D400EX（PCM は 768 kHz まで）を含む多くの DAC は受け付けず、送ると「ジジジ」という雑音になります。DAC が 1411.2 kHz の DoP に対応している場合だけ DSD512 にしてください。ネイティブ DSD で送れるときは、この上限は関係ありません。

開始時の無音（ms） 即

範囲: 0〜2000 / 既定: 300（次の再生開始から）
決めるもの
再生開始時に、本来の音の前に流す無音の長さ。
効果
DAC がレートや形式の切り替えでロックし直す（ミュートが解除される）までの時間を稼ぎ、曲の頭が欠けるのを防ぎます。頭が欠けるなら増やし、曲間の間を詰めたいなら減らします。DSD では停止時にも無音パターン（0x69）を約 60 ms 流してから止め、ポップノイズを防ぎます。

停止時に溜めた分を鳴らし切る 即

オン / オフ（既定: オン）
決めるもの
再生ソフトが停止（stop）したとき、リングに溜まっているまだ鳴っていない分と、最後に受け取ったバッファを鳴らし終えてから止めるか、すぐ捨てて止めるか。
オンにすると再生リストの最後の曲の終わりや、次の曲でサンプルレートが変わって開き直す直前の曲の終わりが欠けません。代わりに、停止ボタンやシークの反応が、溜めていた量（先読みモードで最大 2 秒）だけ遅れます。同期モードでは数十 ms です。
オフにすると停止・シークは即座に反応しますが、溜めていた分は捨てるので、先読みモードでは曲の終わりが最大で先読み量の秒数だけ欠けることがあります。

KS で開けないときは WASAPI 排他に自動で切り替える 開

オン / オフ（既定: オン）
決めるもの
KS のピンが開けないとき（Windows の共有モードがデバイスを使っているなど）に、WASAPI 排他で鳴らすか、エラーにするか。切り替わったときはパネル下部のメッセージに出ます。KS で鳴っていることを確実にしたいときはオフにします。

音の好みから設定を探す

先に大事なこと: OtonumaASIO はビットパーフェクトなので、どの設定でも DAC に届くデータは同じです（パネルの「パイプライン内ビット一致」で確認できます）。そのうえで音の印象が変わるという報告は多くありますが、非同期 USB DAC でそれが測定として裏付けられた例はほとんどありません。考えられる経路は、PC の動き方（起床の頻度・CPU 負荷・電源の揺れ）が USB ケーブルやグラウンドを通る電気的なノイズとして DAC に影響する、というものです。以下は「そう言われることが多い傾向」で、効く保証はありません。必ず ABX で、本当に聞き分けられるかを確かめてください。

音色を確実に変えられるのは DAC 側の設定

データそのものに手を入れるのは DAC 内部のデジタルフィルターです。D400EX には PCM フィルター（6 種類）と DSD フィルター（Wide / Narrow）の選択があり、ここは実際に周波数特性やインパルス応答（リンギング）が変わります。「柔らかい」「広がる」と表現されることが多いのは、一般に Slow Roll-Off や 最小位相系のフィルター（プリリンギングがない、または高域がなだらかに落ちる）です。差はわずかとされますが、測定上の違いがある分、パラメータ調整より確実です。PCM を DSD に変換して再生する（アップサンプリング）のも、データ自体が変わるので音色に影響します。

探し方の手順

  1. まず WASAPI 排他・既定値で鳴らし、プリセット「基準」として保存します。
  2. 一度に 1 項目だけ変え、別名のプリセットで保存します（例:「KS 10Hz」「KS 300Hz」）。
  3. アンダーランが 0 のまま安定することを確認します（アンダーランがあると、それ自体が音の違いになってしまいます）。
  4. 2 つのプリセットで ABX を 10〜20 回行い、p < 0.05 になるかを見ます。偶然の範囲なら、その項目は「どちらでもよい」と判断できます。

DSD

  • 再生ソフトからは ASIO ネイティブ DSD（ASIOSTDSDInt8MSB1）で受け取ります。
  • 出口がネイティブ対応でなければ DoP に包みます。DoP の目印は無音部分も含めて途切れず交互に付けます。
  • 停止時は DSD の無音パターン（0x69）を約 60 ms 流してから止めます。
  • DSD のとき再生ソフトへ提示するバッファは、DSD レートに比例させて最低約 5.8 ms ぶんにしています。
  • 高いレートの DoP（DSD256 → 705.6 kHz など）は、DAC とドライバがその PCM レートを受け付けることが前提です。DoP 上限（既定 DSD256）を超える DSD は、DoP の経路では再生ソフトに非対応と返します。それより上はネイティブ DSD（ASIO 中継）で再生してください。

計測の読み方（パネル右上）

表示意味と見方
経路（1 行目）再生ソフト名 → レート・形式（PCM / DSD→DoP / DSD ネイティブ）→ ビット深度（有効 / コンテナ）→ 出力方式 → デバイス名。
状態（2 行目）受け渡し周期の指定値 → 実効値、1 回のフレーム数、ホスト側バッファ、再生ソフトに報告している遅延。
出口の詳細（3 行目）例:「KS パケット方式 / 32/32 bit / 48 フレーム × 4 個」。末尾は再生ソフトからの受け取り方（outputReady / その場で書き込み / 後から書き込み）。
リング残量今溜まっている量 / 目標 / 容量。残量が 0 近くを行き来していたら余裕不足です。
アンダーラン回数と直近の時刻。リングが空になった、WaveRT で追い越された、KS パケットが全部空になった、のいずれか。0 が正常です。
出力スレッド起床間隔期待値（1 回の量の時間）と実際の平均、期待値とのずれの中央値・99%値・最大値（µs）と、そのヒストグラム（対数目盛）。ずれが期待値の半分を超えるような山があると、アンダーランの予備軍です。
CPU出力スレッドの CPU 使用率（ASIO 中継では表示されません）。タイマー＋スピンではほぼ 1 コア分になります。

ブラインド A/B（ABX）

  1. 比べたい 2 つの設定をプリセットに保存します。出力方式・デバイス・ホスト側バッファ・DSD の送り方は同じにしてください（これらは再生ソフトの再初期化が必要で、切り替え方で判別できてしまうため）。
  2. A・B・回数を選んで、再生しながら「開始」。
  3. 毎回パネルが X = A か B かを乱数で決め、伏せたまま切り替えます。「A を聴く」「B を聴く」「X を聴く」で何度でも聴き直せます。どの切り替えでも必ず同じ「開き直し」をするので、途切れ方で判別はできません。
  4. 「X は A」「X は B」で答えます。
  5. 終わると正解数と、偶然でそれ以上当たる確率（二項検定の p 値）を表示し、元の設定に戻します。「CSV 保存」で記録できます。
回数p < 0.05 に必要な正解数
10 回9 回以上
16 回12 回以上
20 回15 回以上

試験のしかた

asiohosttest はドライバを読み込んで正弦波またはランプ信号を流す簡易ホストです。

asiohosttest --list                                   登録されている ASIO ドライバの一覧
asiohosttest --rate 96000 --seconds 10 --pattern sine 1 kHz の正弦波（実機の音出し確認）
asiohosttest --dsd --rate 2822400                     DSD64 のランプ信号
asiohosttest --dll OtonumaASIO64.dll ...          登録せずに DLL を直接読み込む
asiohosttest --lazy / --outready / --strict           後から埋める / outputReady で知らせる /
                                                      通知を受けたら開き直す再生ソフトを真似る

null 出力でビット一致を確かめる手順:

  1. パネルで出力方式を「null（試験用）」にして適用。
  2. set OTO_NULL_DUMP=C:\temp\dump.raw のあと asiohosttest --rate 44100 --seconds 5
  3. asiohosttest --verify C:\temp\dump.raw --bits 32（DSD は --dsd も付ける）で「不一致 0」なら一致。OTO_NULL_BITS=24 / 16 でコンテナ形式を変えられます。

困ったとき

症状原因と対処
再生ソフトに OtonumaASIO が出ないotonumareg status で登録を確認。32bit の再生ソフトには 32bit 版 DLL の登録が必要です。
init に失敗する別の再生ソフトが使用中です（同時に動けるのは 1 つ）。ウイルス対策ソフトのブロックも確認してください。
KS で開けないWindows の既定のデバイスを別の出力先にします。自動切替がオンなら WASAPI 排他で鳴り、メッセージ欄に理由が出ます。
音飛びするアンダーランの回数を見ます。増えていれば余裕不足なので、受け渡し周期を下げる・KS キュー深さを増やす・ホスト側バッファを増やす・先読みモードにする、の順に試します。増えていないのに飛ぶ場合は、パネル右上の 3 行を添えて報告してください。
WASAPI 排他で周期を上げると飛ぶイベント駆動ではドライバ内のバッファ長が周期と同じになるため、最小周期付近では余裕がありません。少し下げるか、タイマー駆動にします。
DSD で雑音しか出ないDoP のレート（DSD ÷ 16）を DAC が受け付けていない可能性があります。「DoP 上限」を DAC が対応する範囲（D400EX なら DSD256）にするか、ASIO 中継のネイティブ DSD を使ってください。
先読み中に、再生ソフトが曲の途中で次の曲を表示する先読みの仕組み上避けられません（ポンプモード・先読み量）。気になる場合は同期モードにするか、先読み量を減らしてください。
曲の頭が欠ける開始時の無音を増やします。

内部仕様

  • 設定: %APPDATA%\OtonumaASIO\settings.json（current = 今の設定、presets = プリセット、devices = デバイスごとの最終設定）。
  • 計測: 共有メモリ Local\OtonumaASIO.Telemetry（DLL が 100 ms ごとに書き、パネルは読むだけ）。
  • 操作: 名前付きパイプ \\.\pipe\OtonumaASIO.Control（PING / GET / SET {json} / SETQ {json} / REOPEN / VENDORPANEL）。
  • スレッド: ポンプ（再生ソフトを呼ぶ、MMCSS Pro Audio）／出力（出口ごとの送り出し、設定した優先度）／計測（低優先度）／管理（デバイスの開閉、ベンダー ASIO のためのメッセージループ）／操作パイプ。出力スレッドではメモリ確保・ロック・ログ出力をしません。
  • 再生ソフトからの受け取り: ASIO の規約では、再生ソフトはバッファを「次の呼び出しまでに」埋めればよいので、outputReady で知らせるソフトは知らせを受けて、その場で埋めるソフトは戻った直後に、後から埋めるソフトは 3/4 周期待ってから受け取ります（自動判定）。
  • 再生ソフトへの通知: 遅延変更の通知は、再生中に設定変更で遅延が実際に変わったときだけ 1 回送ります。再同期要求は送りません（通知を受けて開き直す再生ソフトで、開き直しが繰り返されるのを防ぐため）。
